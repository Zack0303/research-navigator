# Literature-review setup

For students starting a literature review chapter or a stand-alone review paper. The goal is a review that answers a real question with a traceable method, at a workload the student can finish.

## 1. Start from the question, not the method

- Write the review question and its anchor (checks.md, C1). Who needs this review answered, and why?
- Pick the review type to fit the question and the time available:
  - **Narrative / critical** — build an argument from key works; flexible, must still state how works were found.
  - **Scoping** — map what exists in a broad or new area; descriptive, no quality ranking needed.
  - **Systematic** — answer a focused question with a pre-specified, reproducible search and selection; most work.
  - **Rapid** — systematic shortcuts, stated openly, when time is short.
- Do not call a review "systematic" until the search and screening are actually done as planned. Say "designed" before that.

## 2. Check the nearest existing reviews first (C2)

Find the closest 3–5 reviews before designing anything. If one already answers the question, the contribution must be something else: a newer period, a different setting, an analysis they did not do, or a test of their claims. A new taxonomy or step grouping is rarely enough on its own.

## 3. Pilot before freezing (C5)

- Draft search strings with the student; do not claim to have run them unless you did, with a recorded count.
- Ask the student to run the counts in each database and screen a sample of about 50 titles/abstracts, timing it.
- Estimate total screening effort from that rate. If it is far beyond the time available, narrow the question (and run C1: does the narrower question keep the purpose?), not just the string.
- Keep every run: date, database, exact string, filters, count, export file. An unknown count stays blank, never zero.

## 4. Design extraction that describes before it judges (C4)

- **Descriptive fields** record what each study did: aim, setting, data source, participants, method, evaluation type, reported outcomes. Each field allows `not reported`, `unclear`, `not accessed`, `not applicable`.
- **Appraisal** asks how well the evidence supports each study's own main claim. Choose which claims to appraise in depth by a rule fixed before reading results (e.g. the main claim in the abstract), and apply it to positive and negative results alike.
- Avoid a single ladder that ranks studies by deployment, data realism or business impact. Record those as separate facts. A benchmark study is not a failed industry study.
- Calibrate: two people code the same 3–5 papers, compare, fix definitions, then code the rest.

## 5. Synthesise honestly

- Report counts with denominators and the unit (studies, reports, systems).
- Separate what studies show, what authors propose, and what the reviewer infers.
- If the evidence does not support the expected story, change the story.
- Few papers reporting something does not mean it rarely happens; confidentiality and publication habits shape what is reported.
- Say "we focus on X" rather than "the literature concentrates on X" when the focus came from your search choices.

## 6. Human roles

AI can suggest search terms, draft screening decisions and extract candidate fields. A human researcher makes and records every inclusion decision and checks every extracted fact used in the text. Another AI session is not an independent second reviewer.
